# Архитектура Typing Arena AI

**Статус: предложение до реализации. Дата: 2026-10-11.**

## 1. Архитектурный подход

Модульный монолит с выделенным realtime-процессом. Одна бизнес-модель, один репозиторий, один владелец миграций, одна основная БД. Не нужны Kubernetes, Kafka или отдельный микросервис для каждой функции.

```text
Браузер
  ├─ HTTPS → Next.js: страницы, обычный API, авторизация, AI
  └─ WSS   → Node.js / Fastify / Socket.IO: очередь, комнаты, гонки
                    │
           Общие серверные пакеты
       auth / domain / metrics / contracts / db
                    │
          PostgreSQL — постоянные данные
          Redis — временная очередь, presence, лимиты (этап 6)
                    │
          Worker — фоновые задачи (по необходимости, этап 7)
                    │
          OpenAI / почтовый провайдер — только серверный доступ
```

В production один reverse proxy публикует сайт и Socket.IO под одним origin. Это упрощает сессии, CORS и эксплуатацию. WebSocket-процесс должен быть постоянно работающим: размещение всего проекта исключительно в краткоживущих serverless-функциях не подходит.

До этапа 6 realtime и Redis не обязательны. До появления фоновых задач отдельный worker не запускается. Учебные серверные маршруты и realtime используют один пакет метрик, но обычная практика не требует WebSocket.

## 4. Единая методика результатов

### 4.1. Определения

- `T` — фактическая длительность в секундах. Для временного теста/гонки это установленная длительность; остановка раньше даёт прерванную, а не рейтинговую попытку. В упражнении до завершения текста — активное время от первого символа до конца, с явно указанной политикой пауз.
- `C` — количество правильных символов в конечном буфере, совпадающих с эталоном на той же позиции. Повторный набор ранее удалённого символа не увеличивает этот счётчик сверх конечного результата.
- `A` — число всех попыток ввода символа.
- `H` — число попыток ввода, правильных в момент нажатия на соответствующей позиции.
- `E = A − H` — ошибочные попытки, включая впоследствии исправленные.
- Backspace учитывается отдельно. Shift, Ctrl, Alt, стрелки и Backspace не являются попытками ввода символа и не включаются в знаменатель точности.

Формулы:

```text
CPM = C × 60 / T
WPM = CPM / 5
Accuracy = H / A × 100%
Errors = A − H
```

При `A = 0` точность не определена: показываем «—», не 100%. При `T ≤ 0` результат недействителен. Сравнение победителей использует целочисленные значения и дроби без округления; округляется только отображение.

**Пример:** эталон `кот`, ввод `к`, `а` (ошибка), Backspace, `о`, `т`. Тогда `C=3`, `A=4`, `H=3`, `E=1`, точность 75%. При длительности 15 секунд: CPM=12, WPM=2,4.

**Защита от накрутки:** ввод `к`, Backspace, `к`, `о`, `т` даст `C=3`, а не 4, при `A=4`, `H=4`, точности 100%. Лишнее удаление не является ошибкой символа, но увеличивает затраты времени и счётчик Backspace.

### 4.2. Что именно проверяет сервер

Сервер выдаёт идентификатор сессии, неизменяемый текст, язык, режим, длительность и версию правил. Браузер передаёт упорядоченные операции ввода с последовательными номерами. Сервер воспроизводит вставки/удаления, сверяет позиции с эталоном и вычисляет значения самостоятельно.

**Передавать только `correctChars`, `accuracy` или готовый CPM недостаточно:** правдоподобная подделка таких чисел не позволяет проверить текст. Клиентские показатели нужны лишь для мгновенного интерфейса; итог считается из принятых сервером операций.

Для практики операции отправляются пакетами через HTTP; её временные данные дают базовую, не абсолютную проверку. Для рейтингового заезда поток принимается realtime-сервером в течение серверного окна. Клиентские timestamps полезны для педагогической диагностики, но не определяют дедлайн матча.

RU/EN, длительность, режим, сложность, версия текста и методики сохраняются с каждым результатом. Не сравнивать короткое упражнение на одну букву с рекордом набора предложений. Аналитика фильтруется по сопоставимым условиям; тренировочные результаты не становятся автоматически публичными рекордами.

Тексты нормализуются в NFC. `ё` не подменяется `е`. Пробелы и пунктуация — символы. В рейтинговом режиме нет произвольного перехода курсора, вставки буфера или замены выделения; доступные операции — одиночный ввод и удаление последнего символа. Для IME и экранных клавиатур нужна отдельная политика; они не выдаются за проверенную физическую десятипальцевую печать.

## 6. Гонки и честный рейтинг

### 6.1. Состояния и протокол

```text
WAITING → READY → COUNTDOWN → RUNNING → FINALIZING → FINISHED
                      ↘ CANCELLED / ABORTED
                                  ↘ UNDER_REVIEW
```

Состояния очереди и состояния матча — разные сущности. Подключение socket само по себе не означает участие в матче. Команды `queue:join`, `queue:leave`, `room:join`, `match:ready`, `input:batch`, `match:resume` проверяют текущего пользователя, членство, статус, номер последовательности и допустимый payload. События сервера содержат версию состояния.

Для первой версии — один realtime-инстанс. Redis хранит присутствие и очередь с TTL; PostgreSQL — матчи, принятые пакеты/контрольные точки и финальные результаты. Подтверждённые важные операции не существуют только в памяти процесса. Перезапуск сервера не должен угадывать итог: незавершённый матч восстанавливается по журналу либо отменяется без рейтинга по зафиксированному правилу.

В MVP аутентификация WSS выполняется стандартной защищённой same-origin cookie с серверной проверкой сессии и allowlist Origin. Секрет не читается клиентским JavaScript и не помещается в URL. При будущих разных origin возможен короткоживущий одноразовый ticket, полученный аутентифицированным POST и использованный через handshake; не постоянный bearer token в query string.

### 6.2. Время, reconnect и сетевые ограничения

- Сервер назначает общий `startsAt` после готовности обоих игроков и отсчёта 3–2–1; клиент только отображает время.
- Оба получают один неизменяемый текст и правила; текста достаточно на всю выбранную длительность.
- Принимаются только операции после старта и до серверного дедлайна. Присланное после дедлайна не становится своевременным из-за изменённого клиентского времени.
- Малые пакеты ввода, sequence, ack и повторная отправка ещё актуальных пакетов; повтор одного пакета не добавляет символов второй раз.
- Сетевой reconnect не ставит гонку на паузу. Возврат запрашивает серверный snapshot и последний принятый sequence; клиентские offline-операции после окна не пересчитывают прошлое.
- Для первой версии предлагается окно переподключения 10 секунд. Явный выход — surrender; более длительное отсутствие — техническое поражение в дуэли. Эти правила показываются перед стартом и проверяются тестами.
- Короткие обрывы сети могут повлиять на результат. Полной компенсации задержки без риска злоупотреблений не обещаем. При сбое сервера матч отменяется без изменения рейтинга.
- Socket.IO recovery — удобство, не гарантия. Для нескольких инстансов требуется отдельное решение, например Redis Streams adapter; обычный Redis pub/sub adapter не даёт той же recovery-гарантии.

### 6.3. Победитель и рейтинг

Основной критерий — `C`; при равенстве — точность; при полном равенстве — ничья. До сравнения применяются техническое поражение, дисквалификация и статус review согласно публичным правилам. Финализация результатов, ledger рейтинга и наград — атомарная транзакция с уникальными ограничениями. Повторный HTTP-запрос, socket event или фоновое задание не повторяет начисление.

Предлагается Elo для публичных проверенных дуэлей: начальная оценка 1000, стартовый K=32 как настраиваемая продуктовая гипотеза. Подбор строго по языку и длительности; рейтинг — основное окно, недавние CPM и точность в сопоставимых тестах — мягкое предпочтение. Окно рейтинга расширяется со временем ожидания, но язык никогда не смешивается.

Приватные матчи, быстрые реванши с тем же соперником и групповые гонки первоначально нерейтинговые: это честное ограничение против договорных побед, а не отсутствие реальных результатов. Турнирные итоги считаются отдельно; включение их в Elo требует отдельного правила и тестов.

У каждого языка собственные rating и league. Дневной/недельный/месячный рейтинг сортируется по полученным рейтинговым очкам за период, «всё время» — по текущему Elo. Показатель сортировки явно назван. CPM/точность/победы в строке имеют собственный заданный период. Исторические рейтинги пересчитываются только по контролируемой процедуре с аудитом, не произвольным изменением одного числа.

### 6.4. Антифрод

Серверная выдача текста и challenge, replay операций, единый таймер, лимит payload, последовательности, одно активное рейтинговое участие, отсутствие повторных результатов, проверка принадлежности сессии, контроль повторных пар, ограничение скорости запросов, бан/отзыв сессии и проверка на каждом чувствительном действии.

Высокий CPM, слишком регулярные интервалы, массовые вставки и другие аномалии — сигналы проверки, а не доказательство бота. Потеря фокуса не равна мошенничеству. Не банить автоматически только за скорость или особенности доступности. Отмеченные результаты не влияют на рейтинг до решения; необходимы журнал оснований и процедура обжалования.

`event.isTrusted`, скрытые поля и JavaScript на клиенте не доказывают человеческий ввод. Полной защиты от модифицированного клиента не будет. Необходимо честно описать границы защиты.

## 7. AI-тренер

Два слоя:

1. Детерминированные метрики, минимальная достаточность данных, выбор целевых клавиш/упражнений, правила прогресса и резервный план.
2. OpenAI: понятная интерпретация, ответы на вопросы, объяснение выбора и ограниченная персонализация плана.

Сервер формирует агрегированный контекст по одному пользователю и раскладке: количество наблюдений, последние результаты, ошибки по ожидаемым клавишам, медленные сочетания, Backspace, динамика, цель, результаты матчей. Email, пароль, чужие профили, секреты и административные данные не передаются. Для сравнения RU/EN берутся только явно существующие показатели обоих языков; одной общей оценки навыка нет.

После одной диагностики можно дать предварительный план с оговоркой об ограниченности данных. Выводы о плато, темпе прогресса и сроках требуют нескольких сопоставимых занятий. Не вводится произвольный запрет AI до 10 сессий. При отсутствии наблюдений предлагается тест, а не выдумываются результаты.

Responses API, Structured Outputs, строгая схема результата, серверная проверка допустимых exerciseId, длительности и evidence refs. Числовые карточки формируются сервером; AI не является источником рекордов или расчётов. Недостаточно просто задать JSON Schema: проверяются также отказ, незавершённый ответ и смысловые ограничения. Пользовательские тексты рассматриваются как данные, не как инструкции системе. У тренера нет инструментов смены ролей, рейтинга или прямого выполнения SQL.

Бюджет:

- `AI_ENABLED=false` до настройки владельцем; без положительного бюджета платные запросы не разрешены.
- Лимиты количества запросов на пользователя/день, output tokens, стоимости на пользователя и общего дневного/месячного бюджета.
- Атомарное резервирование верхней оценки стоимости до вызова API, затем сверка по usage и актуальному прайсу. Параллельные запросы не обходят остаток.
- Кэш по версии статистики, цели, prompt и модели; ограниченные retries, timeout и идемпотентный анализ одного результата.
- Использование и расчётная стоимость видны владельцу; сверка с биллингом провайдера обязательна, оценки не объявляются бухгалтерски точными.
- При сбое/лимите открытое сообщение «Алгоритмическая рекомендация: AI временно недоступен». Обучение, расчёты и гонки продолжаются.

## 8. Безопасность, приватность и эксплуатация

Better Auth используется как библиотека, а не собственная криптография. Верифицированные email, безопасный password hashing библиотеки либо поддерживаемая проверенная конфигурация, одноразовое восстановление пароля, защищённые cookies, отзыв сессий после блокировки. Социальные аккаунты не связываются только по неподтверждённому совпадению email.

Роли: USER, MODERATOR, ADMIN, OWNER. Сервер проверяет и роль, и разрешённую операцию, и принадлежность объекта. OWNER назначается одноразовой CLI-командой существующему подтверждённому пользователю по ID; без публичного endpoint, дефолтного пароля или автоматического повышения по произвольному email. Повторный bootstrap при существующем владельце отклоняется. Лишение последнего владельца прав запрещено.

TOTP и recovery-коды обязательны для владельца/администратора. Свежая подтверждённая 2FA-сессия требуется для `/admin` и административных API **даже после Google OAuth**: документация Better Auth предупреждает, что стандартное применение 2FA не охватывает все social flows автоматически. Нельзя проверять только факт `twoFactorEnabled` — важна проверка текущей сессии. TOTP secrets защищаются серверным шифрованием, recovery-коды и ключи не журналируются.

Журнал действий добавляется сервером, неизменяем из административного интерфейса. Изменения ролей, блокировок, контента, рейтинга, турниров и AI-настроек содержат автора, причину и время без секретов. Для более сильных требований — экспорт в отдельно защищённое хранилище.

Публичные DTO только по allowlist: nickname, разрешённый avatar, публичные показатели. Email не попадает в profiles/leaderboards/search. Приватность применяется на сервере. Пользователь заранее понимает, что публичный соревновательный результат может оставаться частью истории матча.

Не записывать нажатия вне активного поля тренажёра. Предлагаемый срок сырых событий — 7 дней; для спорных результатов до 30 дней с ограниченным доступом, затем агрегаты. Сроки настраиваются и публикуются. Удаление аккаунта удаляет/анонимизирует PII и учебные данные; сохранение обезличенной соревновательной истории описывается в политике.

CSP, HSTS после HTTPS, безопасные заголовки, лимиты запросов/размеров, sanitization контента, защита загрузки аватаров, отсутствие secret в `NEXT_PUBLIC_*`, сканирование зависимостей и secret scanning. В первой версии можно использовать генерируемый аватар без upload; загрузка файлов добавляется только с валидацией, перекодированием и безопасным хранением.

Deployment: reverse proxy + web + realtime + worker по необходимости; PostgreSQL с volume/backups; Redis не является единственной копией важного результата. Миграции одним контролируемым процессом, health/readiness endpoints, структурированные логи без PII, мониторинг ошибок/latency/AI budget, TLS, проверка восстановления бэкапа и план rollback. Покупки инфраструктуры не выполняются без согласования.
